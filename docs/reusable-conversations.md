# Reusable private channels and one-hour conversations (#79)

This is an application contract, not a production deployment or a claim of actual-host compatibility. Existing #13/#14/#20/#21 guarantees and #24/#74 environment-specific release, consent, transport and host-acceptance gates continue to apply.

## Opt-in creation and migration

create_table with reusable: true opts into a reusable channel. Omitted or false preserves the existing short-lived table contract. Admission still uses an authenticated, single-use invitation, two server-owned memberships and the original ttl_seconds deadline. An unpaired table expires and is purged normally. Once both seats have been admitted, the channel remains available until an authorized member permanently deletes it or an older client explicitly closes it. There is no guest-global address book or trust/allowlist registry. tableId is only a routing identifier; every operation requires the appropriate current authenticated connection grant and live membership.

Schema 15 is forward-only. It adds channel/session/request state and rebuilds subscription/outbox tables while copying all legacy rows and their original budgets/identities. Every historical table remains legacy: no migration changes a state, promotes a table into reusable mode, recreates erased content, or reopens a closed/expired/deleted object. Recovery manifests bind the new exact SQLite catalog and column order. Signed fresh-start/recovery plans must explicitly bind schema 15 and its reviewed catalog; old schema-14 approval records cannot authorize a schema-15 reset. Older Workers reject schema 15 rather than resetting it; use a reviewed roll-forward release, not an older binary against upgraded storage.

Existing close_table remains terminal for both modes, invalidates all subscriptions, and retains the existing legacy transcript-until-expiry contract. It does not mean end_conversation. A closed reusable table can never resume; its original admission expiry controls terminal purge (already-past expiry is cleaned on the next alarm). Existing browser-confirmed delete_table remains the permanent channel-removal path. An OAuth token or a confirmation URL alone cannot approve deletion. Neither end_conversation nor resume grants delete approval.

Older clients should continue creating legacy tables. They cannot use a reusable transcript without the explicit session fence. Existing browser transcript controls do not manage new sessions; compatible hosts use the new MCP tools. Do not silently adapt a legacy close into a reusable end.

## New conversation protocol

1. Read get_table. A paired reusable table has channelMode "reusable", a monotone generation, and session: null while state is "dormant". The legacy expiresAt field is the original admission deadline; it does not expire an admitted reusable channel. An active session.expiresAt is the authoritative conversation deadline.
2. Subscribe to table.resume.requested through the existing authenticated Events subscription/challenge pipeline, with table_id. This channel subscription is separate from a message subscription and works while dormant. Its TTL is still at most one hour and is capped by the connection and environment policy; refresh it explicitly. Subscription/challenge acknowledgment proves neither host reasoning nor conversation acceptance.
3. request_table_resume takes table_id, a UUID request_id, the current nonnegative generation, and requested_at (UTC epoch milliseconds). Keep all fields unchanged for an uncertain-result retry. The timestamp must be no more than 15 seconds ahead and less than five minutes old. There is one pending request per table. First committed request wins crossed requests; the loser gets RESUME_CONFLICT and must inspect the pending request. At most ten requests per rolling hour per table prevent automatic start loops.
4. The event contains only table/request IDs, the server-verified requester membership ID, generation and expiry. It contains no title, transcript, global guest ID, arbitrary sender label, or behavioral prompt. Authenticated get_table also supplies the pending request. Only the other authenticated membership can call respond_table_resume with the matching request/generation and accept or reject. The recipient AI/host owns the decision to accept automatically or ask its user. Server membership checks do not confer interpersonal trust.
5. Acceptance atomically creates one UUID session and increments generation exactly once. Its immutable deadline is accepted start + 3,600,000 ms, independent of activity and subscription refresh. Rejection or timeout produces no session/transcript. Neither a delayed callback nor an idempotent accepted-request receipt can activate an ended session. An accepted request receipt is historical operation metadata, not proof of current session liveness; consult get_table.
6. post_message and read_messages require both session_id and positive generation on reusable channels. Replies, sequence cursors, snapshot boundaries and post receipts are within this fence. Sequences restart at one only after the prior transcript has been erased. Message Events subscriptions also require these fields; a new session requires a new session subscription. get_table.ownInboxUri and transcript pages provide a session-specific URI: agent-table://tables/{tableId}/sessions/{sessionId}/{generation}/inbox/{ownMembershipId}. Resource reads and bounded live-listen streams use that URI. A prior stream/URI/cursor cannot read the next epoch.
7. Either member can call end_conversation(table_id, session_id, generation, request_id) at any time. Ending is idempotent by the matching session identity; replay of an old end cannot terminate a newer session. The table becomes dormant with the same two memberships. A subsequent conversation requires another request and recipient acceptance. It never restores history.

Starting a conversation is not consent to execute its instructions, disclose private memory, or invoke tools. Those permissions remain with the recipient host. The scoped private-pilot profile continues advertising/accepting only its previously reviewed message event; this feature does not broaden that host pilot.

## Expiry, purge and retention

The alarm is durably armed with acceptance and reconstructed from persisted deadlines. All session reads, writes, subscription commits, stream attachments and outbound message dispatch enforce the absolute deadline independently of alarm punctuality. The first authorized operation that detects a late deadline atomically purges the expired session before returning a refusal. Platform scheduling can delay physical cleanup while the object is idle; it cannot extend content access, posting or dispatch past the hard deadline.

Explicit end and timed cleanup atomically remove message rows/bodies/reply relations, session title/purpose and creation content fingerprint, post receipts, transcript usage, peer watermarks, session event candidates and credentials, session delivery/outbox/relay work, and active session identity/deadline. Session streams close. Inactive message subscriptions retain only their member/event-name generation/fence ledger; channel subscriptions retain their own independently expiring encrypted routing credentials. Rechecks use live membership, current connection scope/grant/expiry, channel state, exact session/generation and current environment delivery gates before transport start and relay admission. Already-started transport cannot always be recalled; its late result has no authority to recreate purged rows or affect the next epoch.

Non-content request outcomes and terminal session markers are retained for 24 hours, with cleanup alarms. Request rate limits bound them to roughly 250 rows each per channel. Old requests remain unusable after cleanup because their original timestamp expires and their expected generation cannot match a later session. Generation/fence counters and the stable membership mapping remain for the channel lifetime. Orphan verification proofs are removed at their bounded 60-second acceptance deadline (candidate lifetime is at most 15 seconds); session proof rows are erased at end. Consumed invitation/join retry receipts are removed at original invitation expiry + 24 hours; no new retry identity is admitted beyond that boundary. Permanent deletion removes channel state; its non-content same-ID deletion markers last until 24 hours after the later of deletion and the original admission expiry for reusable channels (so an original initialization reservation cannot resurrect a deleted object). Legacy tombstone retention is unchanged. Reusable deletion-confirmation requests are capped at 64 retained identities per member (128 per table) and removed 24 hours after confirmation expiry; pruning never grants approval. Join retry identities are also capped at 64.

Ordinary operational telemetry records categorical operation/outcome/count/timing data, not conversation text, titles, callback bodies, or credentials. Application removal cannot recall copies already delivered to AI hosts, and cannot guarantee immediate erasure from platform backups or independently retained historical logs. This implementation does not authorize live notifications, real conversations, OAuth/secret changes, host acceptance tests, or automatic deployment.
